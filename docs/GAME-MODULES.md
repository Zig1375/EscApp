# Модули игр (черновик плана)

Модуль — описание того, что нужно конкретной игре, чтобы она запускалась и работала лучше: настройки запуска,
содержимое бутылки и небольшие правки файлов игры. Модули выпускаются отдельно от приложения, поэтому исправление
для игры доходит до всех без нового релиза EscApp. Модуль развивает нынешнюю базу игр (`KnownGame` в разделе
`games` манифеста), которая умеет только бэкенд и версию Windows.

## Границы

Модуль — **только данные**. Каждое действие выполняет код EscApp из закрытого списка (см. «Действия»); модуль не
может ничего запустить.

Никогда не входит в модуль:
- исполняемые файлы и библиотеки (`.exe`, `.dll`, `.asi`, `.dylib`, `.so` и любой файл с заголовком PE или
  Mach-O), даже с открытым кодом и с благой целью. Обход вроде прокси-DLL для The Witcher 3 (отклоняет конвейер, на
  котором падает конвертер шейдеров D3DMetal) — это работа для рантайма (`EscApp-Runtime`): там он один на всех,
  проверен пробами и выходит с релизом;
- скрипты, которые выполнит игра или система (`.lua`, `.py`, `.js`, `.bat`, `.cmd`, `.ps1`, `.sh`, `.vbs`…);
- кряки, обход DRM и античитов, читы, трейнеры;
- изменённые файлы игры, которые нельзя распространять (exe, архивы с её ресурсами).

## Где лежат и как попадают к игроку

Отдельный репозиторий `Zig1375/EscApp-Games`: правки к играм не смешиваются с кодом приложения, у них свои PR,
проверка в CI и issues с отчётами об играх.

```
EscApp-Games/
├── modules/                 один файл на игру, имя — slug: witcher-3.json, banished.json
├── shared/                  общие модули, от которых зависят модули игр: unreal-4.json, cjk-fonts.json
├── files/<slug>/…           файлы для действия `files` (конфиги, не код)
├── schema/module.schema.json
├── tools/build-index        проверка всех модулей и сборка индекса
└── games.json               индекс, его собирает и коммитит CI; руками не правится
```

Файл модуля не привязан к магазину: одна и та же игра в Steam, GOG и без магазина описывается одним модулем, а
магазины перечислены в `match`.

**Индекс `games.json`** — все модули целиком в одном файле (тысяча игр — десятки килобайт):

```json
{
  "format": 1,
  "generated": "2026-10-26T12:00:00Z",
  "commit": "<коммит EscApp-Games>",
  "modules": [ { "id": "witcher-3", "revision": 3, "…": "модуль целиком" } ]
}
```

- `GameModulesUpdater` (как `ManifestUpdater`) раз в сутки скачивает индекс из `main` и кладёт его в
  `EscApp/GameModules.json`. Копия индекса лежит в приложении (`Resources/game-modules.json`), так что офлайн и на
  новом Mac всё работает. Выбор между копией в приложении и скачанной — как у манифеста: свежее выигрывает.
- **Приватность.** Скачивается весь индекс, игра ищется на Mac. Запрос «модуль для steam/292030» выдал бы GitHub,
  во что человек играет. Только файлы действия `files` качаются по одному и только для игры, которой они нужны (это
  раскрывает одну игру, как `SteamScreenshots` — номер игры в Steam). Каждый такой файл закреплён в индексе по
  SHA-256, и ссылка ведёт на `github.com/Zig1375/EscApp-Games/raw/<commit>/files/…`: хост из того же списка, что у
  манифеста, коммит неизменяемый.
- Индекс с более новым `format` старое приложение не читает и остаётся на прежнем (как манифест).

### Что меняется в манифесте рантаймов

- Раздел `games` (`[KnownGame]`) остаётся читаемым, чтобы старые версии приложения и старые кэши работали, но
  новые записи туда не добавляются. Его нынешние записи (сейчас их нет) переносятся в модули с одним действием
  `launch`.
- Модули ссылаются на компоненты манифеста по имени: `redists` (Visual C++, .NET) и `rtps`. Новых загрузок
  исполняемого модуль не вводит: всё исполняемое по-прежнему только в манифесте рантаймов, закреплённое по SHA-256 и
  с хостов из списка `ManifestUpdater`.
- В будущем, если модулю понадобится компонент, которого нет (например, шрифты), он сначала добавляется в манифест
  рантаймов отдельной правкой.

## Модуль: структура

Формат описан JSON Schema в `EscApp-Games/schema/` (`module.schema.json` для `modules/`, `shared.schema.json` для
`shared/`). Схема проверяет форму; остальные правила (ветки реестра, типы файлов, имена компонентов, уникальность
`match`) проверяет `tools/check`.

```json
{
  "id": "example-game",
  "revision": 3,
  "format": 1,
  "name": "Example Game",
  "note": "Для тех, кто ведёт модуль: почему так. В приложении не показывается.",
  "credits": [{ "what": "значения для Engine.ini", "source": "https://…", "license": "CC0-1.0" }],

  "match": {
    "steam": ["123450"],
    "gog": ["1234567890"],
    "epic": ["namespace:item:app"],
    "exe": [
      { "name": "ExampleGame.exe", "product": "Example Game" },
      { "name": "game.exe", "sha256": ["ab12…", "cd34…"] }
    ]
  },

  "requires": { "minApp": "1.4.0", "modules": ["unreal-4"], "wine": { "from": "11.20" } },

  "fixes": [
    {
      "when": { "wine": { "below": "11.20" } },
      "launch": { "prefer": { "backend": ["dxmt", "dxvk"] } }
    },
    {
      "launch": {
        "require": { "windows": "win7" },
        "prefer": { "retina": "off" },
        "arguments": ["-dx11", "-skipintro"],
        "environment": { "DXVK_FRAME_RATE": "60" }
      },
      "dllOverrides": { "xinput1_3": "builtin" },
      "components": ["vcrun2015-x64"],
      "registry": [
        { "key": "HKCU\\Software\\Example Studio\\Example Game", "name": "FirstRun", "dword": 0 }
      ],
      "configEdits": [
        { "file": "game:Config/Engine.ini", "format": "ini",
          "set": [{ "section": "Display", "key": "VSync", "value": "1" }] }
      ],
      "files": [
        { "add": "game:dxvk.conf", "from": "example-game/dxvk.conf" }
      ]
    }
  ]
}
```

- `id` — slug, постоянный. `revision` растёт при каждой правке модуля: по ней EscApp видит, что применённое
  устарело.
- `format` — версия формата модуля. Старое приложение пропускает модуль с более новым форматом целиком. Неизвестное
  действие внутри знакомого формата пропускается, а не ломает модуль (значения строками, как в `KnownGame`).
- `requires.minApp` — для действий, которые старое приложение выполнило бы не так.
- `requires.modules` и `requires.wine` — зависимости (см. «Зависимости: что скачать для игры»).
- `fixes` — группы действий. У группы может быть условие `when`; группа без него действует всегда.

### Опознание игры (`match`)

По надёжности, сверху вниз; первый совпавший модуль выигрывает, CI не даёт двум модулям совпасть по одному ключу.

1. **Магазин и номер игры в нём:** `store` + `storeID` из `GameRecord` (Steam app id, номер GOG, Epic
   `namespace:item:app`).
2. **GOG без Galaxy:** офлайн-установщик GOG кладёт в папку игры `goggame-<номер>.info`; номер тот же, что у
   игры из Galaxy, и совпадает с `match.gog`. Это новое для `GameIdentifier`: прочитать файл при добавлении игры.
3. **SHA-256 exe** — точная версия.
4. **Имя exe + ProductName** из версии exe — как сейчас `KnownGame`.
5. **Имя exe без ProductName** — только для редких имён. CI отклоняет модуль с общим именем без `product` или
   `sha256` (`game.exe`, `launcher.exe`, `start.exe`, `UnityPlayer`-заготовки, `DOSBox.exe`, `RPG_RT.exe`,
   `Game.exe` RPG Maker…).

Модуль ищется при добавлении игры и заново при смене `exeStamp` (игру обновили), новом индексе и новом рантайме.
Найденный `id` хранится в `GameRecord.module`, чтобы не искать на каждом запуске.

### Условия группы (`when`)

Только то, что EscApp знает до запуска; все условия должны совпасть.

| Условие | Пример | Зачем |
|---|---|---|
| `wine` | `{ "below": "11.20" }`, `{ "from": "11.0" }` | обход бага, который исправлен в нашей сборке Wine |
| `exeSha256` | `["ab12…"]` | правка для одной версии игры |
| `steamBuild` | `{ "from": 1234567 }` | `buildid` из `appmanifest_*.acf` |
| `store` | `["steam"]`, `["none"]` | игре из Steam нужно одно, копии с диска (`none`) — другое |
| `backend` | `["dxvk"]` | переменные DXVK имеют смысл только с DXVK |

## Действия

Закрытый список. Каждое действие — чистая функция «модуль + игра → план» с тестами и тонкий слой, который этот план
выполняет.

### `launch` — настройки запуска

Два уровня силы:
- `prefer` — **подсказка**: первая попытка. Если игра не запустилась, автоподбор (`AttemptJudge`) продолжается
  как обычно, а то, что сработало, запоминается как сейчас.
- `require` — **обязательно**: как выбранное в «Дополнительно» вручную, без перебора. Для того, без чего игра
  точно не работает.

Поля: `backend` (список по порядку), `windows`, `retina`, `scaling`, `chromium`, `fastSync`, `arguments`
(добавляются перед аргументами игрока), `environment`.

`environment` ограничен переменными графики: `DXVK_*`, `DXMT_*`, `MVK_*`, `MTL_*`. Переменные Wine и системы
(`WINE*`, `DYLD_*`, `PATH`, `HOME`…) запрещены все: то, что EscApp делает через них, у модуля есть отдельными
настройками (`fastSync`, `dllOverrides`).

### `dllOverrides` — какую библиотеку брать

`builtin`, `native`, `native,builtin`, `disabled` для названных DLL. `native` значит «библиотека самой игры из её
папки»: модуль своих DLL не приносит. Пишется в `HKCU\Software\Wine\AppDefaults\<exe>\DllOverrides`, то есть только
для exe этой игры, и поэтому подходит и для общей бутылки магазина. Библиотеки бэкенда (`d3d11`, `dxgi`, `d3d9`…)
модуль не трогает: это дело `BackendPlan`.

### `components` — компоненты из манифеста

Id из `redists` манифеста рантаймов (`vcrun14-x64`) или `rtp:<имя>` из `rtps` (`rtp:RPGVXAce`). Ставятся как сейчас (`RedistInstaller`, `RTPInstaller`),
записываются в `REDISTS.json`, на экране запуска называются по имени. Дополняют найденное `RedistNeeds`, а не
заменяют его.

### `registry` — значения реестра

Типы: `string`, `dword`, `qword`, `delete`. Разрешённые ветки:
- `HKCU\Software\Wine\AppDefaults\<exe этой игры>\…` (`Direct3D`, `Mac Driver`, `Version`…);
- `HKCU\Software\<издатель>\…` и `HKLM\Software\<издатель>\…` — собственные настройки и регистрация игры.

Запрещены всегда: `Software\Microsoft`, `Software\Classes`, `Software\Policies`, `Software\Wine` (кроме
`AppDefaults` своего exe), `System`, ветки автозапуска. Значение не длиннее 4 КБ. Пишется через `WineRegistry`, пока
wineserver бутылки остановлен, как сейчас.

### `configEdits` — правка текстовых настроек игры

Только изменение значений в существующих текстовых файлах настроек, без замены файла целиком.

- Форматы: `ini` (секция, ключ, значение, `delete`) и `json` (путь к ключу). XML — позже, если понадобится игре.
- Пути: `game:` (папка игры, где `.escapp`), `documents:` и `appdata:` (общий профиль: правка касается
  сохранений и настроек игры, так что только файлы, которые создала сама игра). Без абсолютных путей, без `..`,
  без перехода по ссылкам наружу.
- Файла ещё нет (игра создаёт его при первом запуске) → правка ждёт следующего запуска. `create: true` разрешает
  создать файл с одними значениями модуля.
- Значения, которые игрок поменял сам после модуля, модуль не перезаписывает: запоминается, что записал модуль, и
  правка повторяется, только пока в файле всё ещё прежнее значение или значение модуля.

### `files` — свой файл рядом с игрой

- `add` — новый файл, которого у игры нет (`dxvk.conf`, файл настроек). Чужой файл с тем же именем не
  перезаписывается.
- `replace` — замена файла данных игры (не кода), только если его SHA-256 совпадает с `expect`, то есть это ровно
  та версия, для которой сделана замена. На этапе 3, и только с лицензией, разрешающей распространение.
- Разрешённые расширения: `.conf`, `.cfg`, `.ini`, `.txt`, `.json`, `.xml`. Любой файл с заголовком PE (`MZ`),
  Mach-O или `#!` отклоняется, даже с разрешённым расширением, и в CI, и в приложении. До 1 МБ на файл.
- В модуле указывается только `from` (путь в `files/`); SHA-256 и размер считает `tools/build-index` и кладёт в
  индекс. Файл скачивается по ссылке из индекса и проверяется по SHA-256 до записи.

## Зависимости: что скачать для игры

Перед запуском EscApp должен знать всё, что игре нужно скачать и поставить, сколько это весит и что уже есть. Это
одна чистая функция с тестами: `GameModuleNeeds.resolve(игра, индекс, манифест, установленное) → Needs`.

### Откуда берутся зависимости

1. **Модуль игры** (`match` совпал): его `components`, `files` и `requires`.
2. **Общие модули**, `requires.modules`. Это модули без `match`, которые сами по себе ни к одной игре не
   применяются: то, что нужно многим играм. Например, `cjk-fonts` (шрифты для японских и китайских игр) или
   `unreal-4` (общие настройки для игр на Unreal Engine 4). Лежат в `shared/`, у них те же поля и действия, кроме
   `match`.
3. **Модули движка**, `match.engine`. Общий модуль может совпасть с игрой сам, без модуля игры, по движку,
   который EscApp уже распознаёт: `unity` (`UnityPlayer.dll`), `unreal` (папка `Engine`), `rpgmaker-xp|vx|vxace`
   (`Game.ini`). Так правка для всех игр на одном движке появляется один раз и доходит и до игр без своего модуля.
4. **Что EscApp находит сам**, как сейчас: Visual C++ и .NET (`RedistNeeds`), RTP (`RPGMakerGame`). Модули это
   дополняют, но не заменяют.
5. **Рантайм**, `requires.wine` (или `requires.features`, например `osync`). Если установленный рантайм старше,
   зависимостью становится новый рантайм из манифеста: его скачивание и установка идут так же, как обновление
   (`RuntimeInstaller`).

### Как собирается список

- **Граф:** зависимости раскрываются до конца, общий модуль может зависеть от другого общего. Глубина не больше 4,
  циклы и ссылки на несуществующий модуль CI не пропускает; приложение при такой ошибке пропускает модуль игры
  целиком и пишет причину в лог.
- **Порядок применения:** сначала зависимости (в порядке перечисления, глубже — раньше), потом модуль движка, потом
  модуль игры. Каждый следующий может переопределить значение предыдущего. Если два общих модуля одного уровня задают
  одно и то же по-разному (один ключ реестра, одна настройка `launch`), это ошибка CI.
- **Каждый модуль вносит в список:**
  - компоненты из манифеста (`components`, а также найденное `RedistNeeds` и RTP);
  - файлы для `files`, с SHA-256 и размером из индекса;
  - рантайм, если `requires.wine` не выполнено.
- **Что уже есть, не качается:** компоненты сверяются с `REDISTS.json` и установленными RTP, рантайм — с
  `RuntimeCatalog`, файлы — с кэшем по SHA-256. В `Needs` попадает только недостающее.
- **Результат** — упорядоченный список с именами для экрана запуска, размером каждого и общим размером, плюс
  отметка, обязательно ли это для запуска.

### Обязательное и необязательное

- По умолчанию всё, что нужно модулю, обязательно: если компонент не скачался, игра не запускается и экран запуска
  говорит, чего не хватило, как сейчас при ошибке установки Visual C++.
- Группа `fixes` с `"optional": true` (например, `dxvk.conf` для лучшей частоты кадров) не держит запуск: без сети
  игра запускается без неё, и группа применяется при следующем запуске.
- Действия без скачивания (`launch`, `dllOverrides`, `registry`, `configEdits`) от сети не зависят и применяются
  всегда.

### Когда считается и качается

- **При добавлении игры** список считается сразу, а скачивание начинается в фоне, чтобы первый запуск не ждал.
  Это раскрывает GitHub одну игру, как сказано в «Где лежат», и только если ей что-то нужно.
- **Перед каждым запуском** список считается заново (это дёшево, без сети): докачивается то, что не успело или
  изменилось.
- **Новый индекс, новая ревизия модуля, новый рантайм, обновление игры** (`exeStamp`) — пересчёт; качаются только
  файлы с новым SHA-256.
- **Экран запуска** называет каждый пункт по имени, как сейчас: «Устанавливаем компоненты, нужные этой игре (1 из
  3)». Для пользователя нет слов «модуль» и «зависимость».

### Кэш файлов

- Файлы модулей лежат в `EscApp/ModuleFiles/<sha256>`: один файл для многих игр скачивается один раз, а одинаковый
  SHA-256 при новой ревизии модуля не качается заново.
- В кэш файл попадает только после проверки SHA-256 и заголовка (не PE, не Mach-O, не `#!`).
- Файл, на который не ссылается ни одна игра в `Games.json`, удаляется при очередной проверке индекса.

### CLI

`escapp module needs <игра>` печатает список: что, откуда, размер, установлено ли уже. Это то же, что видит экран
запуска, и основа для тестов на настоящих играх.

## Порядок приоритетов

От сильного к слабому:

1. Заданное игроком в «Дополнительно» (`chosenBackend`, Windows, аргументы, переменные — переменные игрока
   применяются последними, как требует правило про `WineEnvironment.hostAllowlist`).
2. `launch.require` модуля (модуль игры, потом модуль движка, потом общие модули, от которых они зависят).
3. Что игра уже запомнила здесь (`GameRecord.backend` и прочее из запусков).
4. `launch.prefer` модуля, в том же порядке.
5. `recommended` из `.escapp`.
6. Общие правила (`BackendPlan`, `ExecutableInfo`).

Модуль, который игрок выключил, не применяется совсем.

`require` стоит выше запомненного, потому что обычно появляется после жалобы «игра работала, а потом перестала»; а
`prefer` ниже, чтобы рабочие настройки игрока не ломались от новой ревизии модуля.

## Игры магазинов и общая бутылка

Игры одного магазина живут в бутылке магазина (`Store.bottleID`). Поэтому для них:
- реестр — только ветки `AppDefaults\<exe>` и ветки издателя; общие для бутылки значения валидатор не пропускает;
- компоненты добавляются в бутылку магазина и остаются в ней (для других игр они не вредят);
- `files` и `configEdits` касаются только папки игры. Проверка файлов в Steam вернёт исходные файлы, поэтому правки
  проверяются и применяются заново перед каждым запуском, до команды клиенту;
- `environment` и `arguments` работают, только если EscApp сам запускает клиент для этой игры. Как передать их игре
  через уже работающий клиент — открытый вопрос (см. ниже).

## Учёт и откат

Правило «EscApp удаляет только своё» распространяется на модули.

- **Бутылка:** `MODULES.json` рядом с `REDISTS.json`: какой модуль какой ревизии применён, какие значения реестра
  записаны и какие были до него.
- **Папка игры:** в `.escapp` поле `module` (id, ревизия) и список изменённых файлов с SHA-256 после правки.
  Резервные копии — в `.escapp-backup/` рядом с `.escapp`: они переезжают вместе с папкой игры.
- **Применение идемпотентно:** перед каждым запуском действия сверяются с записанным: уже применённое не
  трогается, откатившееся (проверка файлов в Steam, обновление игры) применяется снова, если условия ещё
  совпадают.
- **Откат** — при выключении модуля игроком, новой ревизии (сначала откат старого, потом новое), удалении игры:
  - файл, чей SHA-256 всё ещё как после правки, возвращается из копии; если он другой, игру обновили, и копия
    просто удаляется;
  - значения реестра возвращаются к прежним, если их с тех пор никто не менял;
  - компоненты остаются: их могли начать использовать, и они ничего не ломают.

## Интерфейс

Без слов «модуль», «патч», «реестр», «DLL».

- На странице игры в «Дополнительно» одна строка: «EscApp знает эту игру и настроил её запуск» и переключатель
  «Использовать настройки EscApp для этой игры» (по умолчанию включено).
- Если модуль задал что-то из «Дополнительно», рядом с этим значением подпись «Рекомендовано для этой игры», как
  объяснение для «Авто» в `GameSettings`.
- Сообщения игроку из модуля — позже (этап 3) и только с переводами на все языки `AppLanguage`.
- Из EscApp ничего не отправляется. Кнопка «Рассказать, как работает игра» открывает в браузере заполненный issue
  в `EscApp-Games` (название, магазин и номер, версия EscApp и Wine, что сработало из `recommended`); отправляет ли
  его игрок, решает он сам.

## Проверка модулей

Одни и те же правила в CI репозитория модулей и в приложении (приложение не доверяет индексу только потому, что его
собрал CI):

- схема `module.schema.json`, известные значения бэкендов и версий Windows;
- уникальность ключей `match` между модулями, запрет общих имён exe без `product` или `sha256`;
- списки разрешённых переменных, веток реестра, путей, расширений; проверка заголовков файлов (PE, Mach-O,
  `#!`); размеры;
- имена компонентов есть в манифесте рантаймов;
- у каждого файла из `files/` есть `credits` с лицензией (SPDX), разрешающей распространение;
- модуль, нарушающий правило, приложение пропускает целиком и пишет причину в лог.

В EscApp — Swift Testing на чистые функции: `GameModuleMatcher` (игра + индекс → модуль), `GameModulePlan` (модуль +
игра + рантайм → действия), `IniEdit`, `JSONEdit`, валидатор. CLI: `escapp module list | show <игра> | apply <игра> |
revert <игра>`.

## Этапы

1. **Основа.** Формат, индекс, `GameModulesUpdater` и копия в приложении, валидатор. `match` по магазину, exe и
   SHA-256. Действия `launch`, `dllOverrides`, `components`. `GameModuleNeeds` с общими модулями и
   `requires.wine`, `escapp module needs`. Перенос `KnownGame`. Строка и переключатель в «Дополнительно».
   Репозиторий `EscApp-Games` с CI.
2. **Правки.** `registry`, `configEdits` (ini, json), `MODULES.json`, `.escapp-backup/`, откат. Опознание GOG
   по `goggame-*.info`. Условия `steamBuild` и `exeSha256`. Модули движка (`match.engine`).
3. **Файлы.** `files` (`add`, затем `replace` с `expect`), кэш `ModuleFiles/`, фоновое скачивание при добавлении
   игры, `optional`, сообщения игроку с переводами, кнопка «Рассказать, как работает игра».

## Открытые вопросы

- Переменные окружения и аргументы для игры магазина, когда клиент уже запущен: перезапускать клиент (как при смене
  бэкенда) или передавать через параметры запуска самого магазина (у Steam — параметры запуска игры в его
  `localconfig.vdf`).
- Версия Windows для отдельной игры в бутылке магазина: проверить, что `AppDefaults\<exe>\Version` в нашей сборке
  Wine действует для игры, запущенной клиентом.
- Нужен ли `when.macOS` и `when.gpu` (M1 против M3 и новее): пока нет ни одной игры, которой это нужно.
- Сколько модулей держать в копии внутри приложения: весь индекс (проще) или только проверенные игры.
