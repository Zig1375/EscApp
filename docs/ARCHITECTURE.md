# EscApp: архитектура (черновик для согласования)

EscApp запускает Windows-игры на Mac с Apple Silicon двойным кликом по `.exe`. Пользователь не видит ни бутылок,
ни Wine. Он видит игру, версию Windows (по умолчанию Windows 10) и кнопку «Играть». Код открытый (Apache-2.0).

## Принятые решения

| Вопрос | Решение |
|---|---|
| Графика в v1 | DirectX 9–11 и DirectDraw: DXVK, DXMT, WineD3D. DirectX 12 (D3DMetal) — в v2 |
| Wine | Пока Wine 11.0 из WhiskyWine 3.1.1 (в нём есть экспорт `macdrv_functions`, без которого не работает DXMT), закреплённый по SHA-256. Дальше — своя сборка с тем же патчем. Gcenx 11.18 отпал: DXMT с ним не работает |
| Бутылки | Одна на игру, клон шаблона через APFS `clonefile` (~20 мс, ~0,6 МБ, проверено опытом) |
| Версия Windows | Значение в реестре бутылки игры, новая бутылка не нужна |
| Сохранения | Общие для всех бутылок (см. «Общий профиль») |
| Магазины | Необязательны. Кнопка «Установить Steam / Epic / GOG Galaxy» |
| Система | macOS 15+, только Apple Silicon |
| Язык | Английский и русский с первого дня (String Catalog) |
| Распространение | DMG с нотаризацией, без sandbox, обновления через Sparkle |
| Лицензия | Apache-2.0. Будущие платные функции — отдельный закрытый модуль поверх открытого ядра |

## Структура проекта

```
EscApp/
├── Package.swift      SwiftPM: EscAppKit (вся логика, без UI, тесты без Wine), EscAppCLI и `escapp`
├── Sources/, Tests/
├── App/               SwiftUI-приложение; Xcode-проект генерируется из project.yml (XcodeGen)
├── runtime/           манифест компонентов и как его обновлять
└── docs/
```

Swift 6 (строгая конкурентность), Swift Testing, SwiftFormat + SwiftLint, CI на GitHub Actions.

Правило для EscAppKit: всё, что можно описать как функцию «вход → результат», так и пишется. Сюда входят окружение
Wine, выбор бэкенда, опознание игры и разбор логов. Процессы, файлы и реестр — тонкий слой поверх.

## Данные на диске

```
~/Library/Application Support/EscApp/
├── Runtime/<id>/          Wine (с Mono и Gecko) + DXVK + DXMT (по одной папке на версию рантайма)
├── Templates/<runtime>/   бутылка-шаблон для этого рантайма (wineboot один раз, ~35 с)
├── Bottles/<game-id>/     клоны шаблона, по одному на игру; у магазинов постоянные id E5CA5704-…-00000000000N
├── Profile/               общий профиль: AppData, Saved Games
├── Games.json             известные игры: id, пути, хеш, настройки, удачный бэкенд
└── Logs/<game-id>/        лог каждого запуска
~/Games/                   сюда установщики ставят игры (в Wine это диск G:)
```

## Сценарий: двойной клик по `game.exe`

1. **Компоненты на месте?** Если нет — экран установки (см. «Компоненты»), потом продолжаем.
2. **Какая это игра?** См. «Опознание игры». Новая игра получает новый `game-id`.
3. **Бутылка.** Если её нет — `clonefile(Templates/<runtime>, Bottles/<game-id>)`. Потом подключаем общий профиль и
   ставим версию Windows.
4. **Анализ exe** (результат кэшируется): разрядность, какой DirectX импортирует (`ddraw`, `d3d8`, `d3d9`, `d3d11`,
   `dxgi`), нужные рантаймы (`msvcp140.dll` → Visual C++, `d3dx9_*.dll` → DirectX 9 runtime), признаки DRM и
   античитов (`steam_api*.dll`, EOS, EAC/BattlEye), 16-битный ли это exe.
5. **Выбор бэкенда:** удачный бэкенд прошлого запуска, иначе база игр, иначе правила (см. ниже). Так же сам решается
   **Retina**: включаем, только если манифест exe объявляет поддержку высокого DPI (`dpiAware`/`dpiAwareness`), иначе
   интерфейс игры стал бы крошечным. Так же сам решается **масштабирование**: если игра просит экран меньше, чем у Mac
   (обычно DirectDraw/DirectX ≤ 9), EscApp не переключает экран Mac, а увеличивает игру сам (см. «Увеличение игры»). В «Дополнительно» у обеих
   настроек есть Авто/Вкл/Выкл.
6. **Графика — свой Wine на каждый бэкенд.** DLL DXVK и DXMT помечены как «встроенные» Wine: из `system32` бутылки
   Wine их не берёт, а `WINEDLLPATH` проверяется только после собственных DLL Wine. Поэтому `wine-dxvk` и `wine-dxmt` —
   APFS-клоны папки `wine` рантайма, в которых DLL бэкенда лежат в `lib/wine/<arch>` (клон почти ничего не весит).
   Игра выбирает графику тем, какой `wine` запускается; в бутылке графических DLL нет. Исключение — заглушка
   `winemetal.dll` в `system32`/`syswow64` для DXMT: без неё Wine не находит его встроенную DLL.
7. **Запуск:** `wine <путь к exe>` напрямую, без `start /unix`, чтобы следить за самой игрой. Рабочая папка — папка игры.
   Окружение — чистая функция: от хоста берётся только белый список переменных, настройки пользователя идут
   последними.
8. **После выхода:** ждём `wineserver -w` (Wine дописывает реестр после выхода игры) и разбираем лог. Если игра упала
   в первые секунды с известной ошибкой — повтор со следующим бэкендом. Сработавший бэкенд запоминаем.

## Проверка при первом запуске

Первый запуск игры — это и есть проверка: EscApp не гоняет отдельные тесты, а запускает игру по очереди с вариантами
настроек, пока один не сработает. Пользователь в это время видит окно «Подбираем настройки для …» с шагами и
попытками (экран 5a в дизайне).

1. Шаги 4–6 сценария выше: анализ exe, рантаймы, порядок бэкендов (сначала база игр, затем правила).
2. **Попытка** = запуск с очередным бэкендом. Попытка удалась, если:
   - процесс игры создал окно на Mac за отведённое время (30 с, для тяжёлых игр больше);
   - после появления окна игра держится 15 с;
   - в логе нет известной смертельной ошибки (`LogDiagnosis`).

   Окно — это окно процесса из папки Wine этой игры на экране (`GameWindows`). Ждать окно 60 с имеет смысл только
   для бэкенда, который у игры ещё не работал: с запомненным бэкендом попытка проваливается, только если игра
   закрылась с ошибкой. Правила решения — чистая функция `AttemptJudge`, цикл попыток — `AutoLaunch`.
3. **Не удалась** — EscApp останавливает игру (`wineserver -k` бутылки) и пробует следующий вариант. В окне видно, что
   было и почему: «DXVK — закрылась через 3 с, ошибка видеорежима».
4. **Удалась** — игра не перезапускается, она просто продолжает работать. EscApp запоминает бэкенд и показывает итог:
   что выбрано и почему, с кнопкой «Изменить».
5. **Ничего не подошло** — честное сообщение с самой понятной причиной из логов и кнопкой «Скопировать отчёт».
   Если лог показывает, что другой бэкенд не поможет (не хватает файла самой игры, античит, DirectX 12), попытки
   заканчиваются сразу. Чтобы в логе были ошибки Wine, игра запускается с `WINEDEBUG=fixme-all`, а не `-all`.
6. Есть «Не проверять, просто запустить» (текущая попытка продолжается без проверки), «Выбрать настройки самому»
   (игра закрывается, открывается её «Дополнительно») и «Отмена».
7. **Окно игры спрятано**, пока идёт подбор: экран подбора (`TuningCover`) накрывает все мониторы окном уровня
   `screenSaver`, выше любых окон Wine, в том числе «поверх всех». Неудачная попытка может открыть и закрыть окно
   игры — пользователь этого не видит. EscApp держит фокус у себя: игра, захватившая мышь, иначе не дала бы
   нажать кнопки. Когда попытка удалась, экран убирается, а окно игры выходит вперёд. Подбор
   (`AutoLaunch.isTuning`) включается только при графике «Авто», когда у игры ещё нет рабочего бэкенда и вариантов
   больше одного; у игр из магазина одна попытка, подбора нет.

**База игр** — список `games` в манифесте: имя exe (и при необходимости ProductName из exe), бэкенд и версия
Windows. Значения хранятся строками, поэтому незнакомый старому приложению бэкенд не ломает чтение манифеста.
Версия Windows из базы применяется только к ещё не запускавшейся игре.

Retina и масштабирование решаются не попытками, а по файлам игры (см. шаг 5 сценария). Повторно проверка
запускается сама, только если игра с запомненными настройками начала падать (например, после обновления Wine).

## Программы на Chromium

NW.js (на нём все игры RPG Maker MV и MZ), Electron и программы со встроенным CEF в Wine на Mac показывают пустое
белое или чёрное окно. Chromium рисует в отдельном GPU-процессе, а его картинка в окно, которое показывает Mac, не
попадает. Ключ `--in-process-gpu` переносит эту работу в браузерный процесс: картинка появляется, ускорение остаётся
(WebGL-игры не теряют скорость). Запасной вариант — программная отрисовка (`--disable-gpu`). Проверено на NW.js 0.92 и
Electron 33 под Wine 11.20.

- **Распознавание по файлам** (`ChromiumApp`, `ExecutableInfo.chromium`): импорт `nw_elf.dll`/`nw.dll` или
  `libcef.dll`, либо рядом с exe лежат `icudtl.dat`, `*.pak` и `libEGL.dll`/`v8_context_snapshot.bin`. Такой
  программе ключ добавляется при каждом запуске. Её импорт `d3d12.dll` (WebGPU) не делает её игрой на DirectX 12:
  рисует она через Direct3D 11.
- **Проверка картинки при первом запуске** (`WindowPicture`, `AttemptJudge.checksPicture`): пока окно держится,
  EscApp раз в секунду снимает его через ScreenCaptureKit. Если окно программы на Chromium (по файлам или по
  GPU-процессу Chromium в бутылке) за 40 с так и не показало ничего, кроме одного цвета, попытка не удалась. Тот же
  бэкенд пробуется с другим способом отрисовки, а удачный вариант запоминается (`GameRecord.chromium`). Для
  остальных игр пустое окно — не провал: у них бывает долгий чёрный экран загрузки.
  - Снимок окна другой программы требует разрешения «Запись экрана». Приложение просит его один раз, при первом
    запуске первой новой игры. Без разрешения проверка пропускается, всё остальное работает как раньше.
  - Окно выбирается по номеру из списка окон macOS (самое большое окно игры), а не из списка ScreenCaptureKit: тот
    отдавал процессу Electron его скрытое окно 500×500.
  - Снимок длится не больше 3 с и не может задержать запуск. CLI крутит главный цикл событий, иначе
    ScreenCaptureKit не отвечает, а без подключения к оконному серверу (`NSApplication.shared`) процесс падает.
- **Магазины, поставленные своим установщиком** (`Store.clientProgram`, `StoreClient.prepareClientProgram`):
  если программа — это `steam.exe`, `EpicGamesLauncher.exe` и т. п. на своём месте в бутылке, с ней делается то же,
  что при установке кнопкой: клиентские ключи; для Steam первое обновление до запуска и обёртка помощника; для Epic
  установка скачанного обновления. Проверено: Steam, поставленный своим `SteamSetup.exe`, с одного загрузчика
  открывается на окне входа.
- **Пустое окно после загрузчика** (`LateBlank`, `AutoLaunch.lateBlank`): на первом запуске проверка не
  заканчивается, когда попытка засчитана. Ещё 3 минуты EscApp раз в 2 с смотрит на самое большое окно игры. Если
  появилось окно, которое 40 с остаётся одного цвета и ни разу не рисовало, а программа к этому времени оказалась
  Chromium (по файлам или по GPU-процессу в бутылке), игра перезапускается с другим способом отрисовки. Окно,
  которое сначала рисовало, а потом почернело, — это экран загрузки самой игры, и он не считается. Проверено
  тестовым загрузчиком: он 18 с показывает своё окно и запускает Electron из подпапки. EscApp поймал пустое окно
  Electron и со второго раза запустил его как надо.
- **Чего пока нет.** Ключи Chromium передаются в командной строке запускаемой программы. Загрузчик, который не
  передаёт свои аргументы дальше, их не донесёт. Такие известные клиенты (магазины) обрабатываются отдельными
  правилами, остальные пока нет. Обёртка `ChromiumHelper` годится только для
  помощников, которые сами являются браузерным процессом (`steamwebhelper`). Если обернуть подпроцесс, Chromium
  не может передать ему дескрипторы, и подпроцесс падает: так у Epic упала сетевая служба.

## Место и размер окна игры

Окна в Wine создаёт сама игра, там, где она просит, и большинство игр не помнит, куда игрок их передвинул и
каким сделал. Поэтому EscApp рядом с каждой игрой (кроме игр из магазинов) запускает в её бутылке маленькую
Windows-программу `window-keeper.exe` (`tools/window-keeper`, `WindowKeeper`):

- она находит процесс игры по имени её exe и следит за самым большим окном с заголовком в бутылке;
- пока игра идёт, записывает его место и размер в `C:\windows\escapp-window.txt` бутылки вместе с размером экрана;
- при следующем запуске ставит окно туда же, дважды, потому что игры часто центрируют окно сразу после создания;
- полноэкранные, свёрнутые и развёрнутые окна не трогает; если размер экрана другой (сменился монитор или режим
  Retina), сохранённое место не применяется;
- заканчивает работу вместе с процессом игры, поэтому бутылка затихает как раньше.

Всё делается изнутри Wine, поэтому разрешения «Универсальный доступ» на Mac не нужно. Сброс Windows игры забывает
сохранённое место. Проверено пробой на Wine 11.20: записанные 1000×700 в (300, 400) окно получило при следующем
запуске (на Mac с Retina это 496×361 точки).

## Прогрев бутылок

Холодный запуск — это в основном сам Wine: wineserver бутылки, службы Windows и процесс рабочего стола, который
нужен первому окну (M2 Max: 1,7 с из 2,2 с). `BottleWarmer` поднимает их заранее, и окно игры появляется через
~0,5 с. Прогретая бутылка — ~117 МБ памяти и меньше 1% одного ядра в простое.

- Греется последняя запущенная игра, когда EscApp в фокусе, и игра под курсором (карточка, на которой курсор
  задержался 0,4 с) или открытая страница игры.
- Бутылку прежней версии Wine прогрев сам переносит на текущую, как это делает запуск, если шаблон текущей версии
  уже готов (клон, секунда-две). Раньше после каждого обновления Wine последняя игра не грелась, пока её не
  запустят хотя бы раз. Не больше двух бутылок, лишняя гасится.
- Через 5 с после потери фокуса EscApp гасятся все. При запуске игры гасятся все, кроме её собственной.
- На Mac с памятью меньше 16 ГБ прогрева нет совсем.
- Бутылку держит живой пустой `cmd /c pause`, который читает из трубы EscApp: если EscApp закроется или упадёт,
  он выйдет сам, и Wine погасит бутылку через несколько секунд.
- Игра забирает бутылку, только когда уже работает (появилось окно, процесс завершился или прошло 10 с): если убрать
  помощника раньше, Wine сразу гасит службы, и выигрыша нет.
- Настройки игры пишутся в реестр до прогрева; перед сменой версии Windows, exe или удалением игры бутылка гасится.

## Опознание игры

Один хеш exe ненадёжен:
- у Unity-игр `game.exe` — одинаковая заготовка Unity, просто переименованная;
- старые игры GOG запускаются через один и тот же `DOSBox.exe`;
- после патча хеш меняется, и игра «потеряла» бы свою бутылку.

Поэтому главный признак игры — **файл `.escapp` в папке игры**, как `.git` у репозитория:

```json
{ "id": "6F1C…", "format": 1 }
```

- Переживает всё, что делают с папкой: перенос, копирование на другой диск (включая exFAT), архивы, облако,
  патчи (патч заменяет exe, но не трогает чужой файл), проверку файлов в Steam.
- Один `.escapp` на папку — одна игра. Лаунчер, сама игра и настройщик из одной папки получают одну бутылку, это правильно.
- **Поиск вверх, как у git:** от папки exe поднимаемся до 3 уровней. Так `Game/bin/x64/game.exe` и
  `Game/launcher.exe` находят один и тот же `Game/.escapp`. Поиск останавливается на общих папках (`~`, `~/Games`,
  `~/Downloads`, `~/Desktop`, корень диска): `.escapp` в них никогда не создаётся и не учитывается.
- **Новый `.escapp`** создаётся при первом запуске в папке игры: это папка exe, но служебные папки (`bin`, `x64`,
  `Win64`, `Binaries`…) пропускаются вверх, так что `Game/bin/x64/game.exe` кладёт `.escapp` в `Game`. У игр на Unreal
  корнем считается папка, где лежит `Engine` (там же их лаунчер). Имя игры пока берётся из имени этой папки.
- **Копия папки:** если `.escapp` с этим id уже есть по другому пути и та папка тоже существует, значит игру скопировали
  (например, моды). Копия получает новый id и свою бутылку.

Других признаков нет: игра опознаётся только по `.escapp`. Последний путь и отпечаток exe (SHA-256 и список файлов
папки) раньше тоже находили игру и могли принять одну игру за другую; их убрали. Если записать `.escapp` нельзя (ISO,
CD, папка только для чтения, общая папка вроде `~/Downloads`), каждый запуск такого exe считается новой игрой. Поле
`fingerprint` в `Games.json` осталось только для чтения старых файлов.

## Бутылки

- **Шаблон** создаётся один раз на рантайм (`wineboot --init`, на Wine 11.18 ~35 с вместе с установкой Mono и
  Gecko, 330 МБ) и после этого не меняется. Он собирается во временной папке и считается готовым, только когда
  записан `TEMPLATE.json`. Клон на игру делается за ~0,04 с (проверено на M2).
- `winemenubuilder` всегда выключен: иначе установщики добавляли бы ярлыки и привязки файлов в сам macOS.
- **Клон на игру** весит ~0,6 МБ. После первого запуска добавляется ~3,3 МБ реестра (`system.reg` Wine переписывает
  целиком) плюс то, что поставила сама игра.
- **Версия Windows** — `HKCU\Software\Wine\Version` в бутылке игры. EscApp правит `user.reg` как текст (миллисекунды
  вместо запуска Wine), поэтому только пока Wine этой бутылки не запущен.
- **Новый рантайм — перенос бутылки** (`BottleMigration`). При следующем запуске игры EscApp делает свежий клон
  нового шаблона и переносит в него то, что изменила игра: файлы, отличающиеся от старого шаблона, и значения
  реестра, отличающиеся от реестра старого шаблона. Сравнение идёт со старым шаблоном, потому что бутылка начиналась
  как его точная копия. Всё прочее в ней принадлежит Wine, и в новом шаблоне уже лежит версия нового Wine.
  - Не переносятся заглушки DLL самого Wine (метка «Wine builtin DLL» после DOS-заголовка) и разделы реестра, которые
    Wine заполняет сам при каждом старте: устройства (`Enum`, `DeviceClasses`, `Class`, `Video`), сетевые карты и
    шрифты. Удалённое игрой не переносится.
  - Новая бутылка собирается рядом со старой и подменяет её одним `renamex_np(RENAME_SWAP)`, поэтому сбой на
    середине оставляет старую бутылку нетронутой.
  - Если старого шаблона уже нет, переносится только то, чего в новом нет совсем.
  - Старый шаблон удаляется, когда на нём не остаётся ни одной бутылки.
  - Проверено на настоящем Wine: бутылка 11.0-2 с поставленной игрой и ключами в HKCU и HKLM переехала на 11.20-1.
    Перенеслась только папка игры, ключи читаются новым Wine, игра запустилась.
- **Размер** считаем сами по реальному расходу. Finder и `du` показывают полный размер каждого клона.

## Общий профиль (сохранения)

- `Documents`, `Desktop`, `Downloads` (а также Музыка, Изображения, Видео) — Wine уже связывает их с папками Mac.
- Ссылки на `EscApp/Profile` делаются один раз в шаблоне; клоны копируют ссылки, а не данные. Проверено на настоящем
  Wine: сохранение, записанное одной игрой в `%APPDATA%`, читается другой игрой и лежит в `EscApp/Profile`.
- `AppData/Roaming`, `AppData/Local`, `AppData/LocalLow`, `Saved Games` — ссылки на `EscApp/Profile/`.
- Имя пользователя Windows одинаковое во всех бутылках и рантаймах. Иначе после смены рантайма сохранения
  «пропадают».
- Исключение: игры, которые пишут сохранения в реестр. Это редкость, в v1 не решаем.

## Компоненты

- **Манифест** (JSON на GitHub Pages): для каждого компонента URL, SHA-256, размер, минимальная версия EscApp и macOS.
  Скачанное без совпадения хеша не ставится.
- Wine (сейчас WhiskyWine 3.1.1, см. таблицу решений), DXVK-macOS 1.10.3 (на 2.x переходить нельзя: нужен Vulkan 1.3), DXMT 0.80 (последняя версия под MIT),
  Докачка при обрыве. Wine Mono и Gecko отдельно не качаются: в сборке Gcenx уже лежат именно те версии, которые ждёт этот Wine.
- **Обновления:** копия манифеста лежит внутри приложения, поэтому первая установка работает без сервера. Раз в
  день (если не выключено в настройках) EscApp скачивает свежий манифест из репозитория (тот же файл в `main`) и
  кэширует его в `EscApp/Manifest.json`. Скачанный манифест может ссылаться только на загрузки с github.com. Новая версия
  рантайма никогда не блокирует игру: EscApp показывает баннер «Доступно обновление» и экран «Настройки → Компоненты»
  (что установлено, версии, лицензии, место на диске, что изменится). Обновление заменяет старый рантайм: после
  установки старый удаляется (`RuntimeInstaller.removeOlder`), а если из него ещё что-то запущено (игра, клиент
  магазина) — при следующем старте EscApp. Бутылки переезжают на новый рантайм при следующем запуске игры; для
  переезда нужен только старый шаблон, не сам рантайм. Ежедневная проверка молчит при ошибке сети, об ошибке
  сообщает только «Проверить обновления».
- **osync** (Wine 11.20 сборка 3 и новее, свойство `features: ["osync"]` у компонента Wine в манифесте): события,
  мьютексы и семафоры обрабатываются внутри процесса, без обращения к wineserver на каждое ожидание (своя реализация,
  `docs/osync.md` в EscApp-Runtime). Включается переменной `WINEOSYNC=1` у wineserver бутылки; её процессы делают то
  же, что сервер. Поэтому все запуски в бутылке берут настройку из одного места,
  `WineEnvironment.fastSync(for:wine:)`: включено, если Wine это умеет, кроме игры, где «Быструю синхронизацию»
  выключили в «Дополнительно». У бутылки магазина всегда включено, потому что её делят клиент и все игры. Перед
  запуском игры `GameLauncher` читает окружение процессов бутылки и, если там настройка другая (остался установщик или
  прогрев до её смены), останавливает их, чтобы wineserver запустился заново с нужной.
- **Rosetta:** проверка при старте. Установка — только после согласия пользователя с лицензией Apple.
- Лицензии всех компонентов показываются в приложении.

## Увеличение игры (масштабирование низких разрешений)

Многие старые игры работают только в маленьком окне (640×480, 800×600) или просят полноэкранный режим такого
разрешения. На Retina-экране такое окно выглядит крошечным, а экран Mac переключать нельзя. EscApp увеличивает такие
игры средствами самого Wine (`GameScaling`), без захвата экрана и без разрешения «Запись экрана». Мышь Wine
пересчитывает сам.

- **Полноэкранные игры.** Без помощи такая игра на современном Mac не запускалась вовсе: Wine искал у экрана Mac
  режим 640×480, не находил его и отказывал. `ChangeDisplaySettings` возвращал −2, а Direct3D 9 не мог создать
  устройство. Поэтому EscApp всегда включает в бутылке `HKCU\Software\Wine\X11 Driver\EmulateModeset`: ключ
  назван по драйверу X11, но его читает ядро Wine (`win32u`) для любого драйвера.
  - Игра видит экран 640×480, экран Mac не меняется.
  - Wine растягивает окно игры на весь экран с сохранением пропорций. Это пересчёт `virt → raw` в `win32u`, а
    поверхности GDI, OpenGL и Vulkan растягивает сам Wine.
  - Проверено пробой `Tests/Fixtures/probes/lowresprobe.c` (GDI и Direct3D 9) на Wine 11.20: окно заняло весь
    экран 1728×1117, игра видела 640×480.
- **Маленькое окно.** Программу, которая не объявляет поддержку высокого DPI, Wine (как и Windows) рисует крупнее,
  когда системный DPI выше 96 (`HKCU\Control Panel\Desktop\LogPixels`). DPI задаётся до запуска, поэтому EscApp
  запоминает размер окна игры (`GameRecord.window`): пока игра на экране, окно замеряется на каждом опросе, а
  после удачного запуска записывается последний замер. Со следующего запуска игра увеличена.
  - Целое кратное для окон до 800×600, иначе дробное — так, чтобы окно поместилось на экране.
  - «Авто» увеличивает, только если окно ниже половины экрана.
  - Проверено: окно 640×480 на втором запуске стало 1280×988 точек, а игра по-прежнему видела 646×512.
- Игры, которые объявляют поддержку высокого DPI, рисуют для Retina сами и не увеличиваются.
- Настройка игры `scaling`: Авто (по умолчанию), Вкл, Выкл. В приложении она на экране «Дополнительно», в CLI —
  `escapp run --scale`. «Выкл» отключает увеличение окна. Полноэкранная игра всё равно растянута на
  весь экран: другого способа показать её на Mac нет.
- Окна игр «поверх всех» (`WS_EX_TOPMOST`, так делают полноэкранные игры) Wine кладёт на уровень окон 21.
  `GameWindows` считает их окнами игры; уровни 24–25 (строка меню и значки в ней) — нет.
- Если этого окажется мало (игра с изменяемым окном, которое не растягивается), остаётся запасной путь из первого
  плана: захват кадров окна через ScreenCaptureKit и вывод увеличенной картинки поверх него.

## Установщики и старые игры

- **Распознавание установщика** (`InstallerKind`) идёт по строкам версии, манифесту и меткам в первых 8 МБ файла:
  Inno Setup, NSIS, InstallShield, а `.msi` — это Windows Installer. Остальные узнаются по имени (`setup*.exe`) или
  описанию. Деинсталляторы (`unins000.exe`) установщиками не считаются.
- **Установка** (`GameInstaller`) идёт в ту бутылку, которая станет бутылкой игры: многие старые игры читают из
  реестра то, что туда записал установщик.
  - Папка игры — обычная папка на Mac (`~/Games/<название>`). Её родитель виден в бутылке как `G:`, и эта ссылка
    остаётся в бутылке навсегда, потому что пути `G:\…` попадают в реестр.
  - Папку получают те установщики, которые её принимают: Inno — `/DIR=`, MSI — `INSTALLDIR=` и похожие свойства,
    NSIS — `/D=`. Для MSI `G:` указывает на саму папку игры, и пакет получает `INSTALLDIR=G:\`: msiexec понимает
    значение с пробелом только в кавычках внутри аргумента, а `wine` их так не передаёт (найдено тестом на Wine). NSIS читает `/D=` из сырой командной строки и только без кавычек, поэтому значение передаётся
    словами, разрезанными по пробелам: `wine` склеивает их обратно без кавычек. Проверено тестовым установщиком
    `Tests/Fixtures/probes/setupprobe.c`, он разбирает строку как NSIS.
  - Установщик закончил, когда затихла вся бутылка (`wineserver -w`): Inno, msiexec и другие отдают работу
    дочерним процессам и сразу выходят.
  - Игру ищут в выбранной папке и в новых папках `drive_c`: многие InstallShield-установщики папку не принимают.
    Рекомендуется цель ярлыка, созданного установщиком (`ShellLink`), иначе программа с именем игры, иначе
    самая большая. Деинсталляторы и распространяемые пакеты (DirectX, VC++) не показываются.
  - Рабочий стол Windows — это рабочий стол Mac, поэтому ярлыки, которые установщик положил туда, EscApp читает
    и удаляет.
  - Обходы бутылки не переходят по ссылкам: `Documents` и `Desktop` ведут в настоящие папки Mac.
- **Тесты на настоящем Wine** (`ESCAPP_INTEGRATION=1`, `OldGameProbeTests.swift`) повторяют всё это на пробах
  из `Tests/Fixtures`:
  - установка с ISO, из MSI (`Tests/Fixtures/installers`) и NSIS-подобного установщика;
  - CD-проба без диска и с BIN/CUE;
  - полноэкранная и оконная пробы с масштабом;
  - перенос бутылки, если в `ESCAPP_HOME` установлены два рантайма.
- **Образы дисков** (`DiscImage`): `hdiutil attach -readonly -nobrowse` в `EscApp/Discs/<uuid>`, без показа в
  Finder. Образ, уже открытый пользователем, используется как есть и не отключается.
  - В бутылке диск `D:` — ссылка на папку образа. `d::` — ссылка на `/dev/rdiskN`: только оттуда Wine читает метку
    диска, а старые игры проверяют её, чтобы убедиться, что их CD вставлен. В реестре диск помечен
    `HKLM\Software\Wine\Drives` `"d:"="cdrom"`.
  - Если игра проверяет CD, образ запоминается в `Games.json` (`disc`). Он подключается перед каждым запуском и
    отключается после игры. Бутылки таких игр не прогреваются.
  - BIN/CUE и другие сырые копии CD (`.img` CloneCD, `.mdf` Alcohol: файл начинается с метки синхронизации
    сектора) `hdiutil` не открывает. `RawDisc` переводит дорожку данных в ISO: из сектора 2352 байт берутся 2048
    байт данных (смещение 16 у MODE1, 24 у MODE2). ISO кэшируется в `EscApp/Discs/Converted`, имя зависит от пути,
    размера и даты образа. У игры записан исходный `.cue`. Звуковые дорожки (музыка многих старых игр) в ISO не
    помещаются: игра работает, но без этой музыки.
- **Игра просит диск.** Wine пишет в лог текст окон-сообщений (`trace+msgbox` в `WINEDEBUG`), а `LogDiagnosis`
  узнаёт в нём просьбу вставить CD на нескольких языках. Окно «вставьте CD» висит, пока игрок его не закроет, и
  считалось бы окном игры. Поэтому цикл запуска читает новые строки лога во время игры, сразу сообщает о просьбе
  (`asksForDisc`) и не считает такой запуск рабочим. Повтор с другим бэкендом не нужен. Приложение тут же
  предлагает «Выбрать образ диска…»: образ привязывается к игре, и игра перезапускается уже с диском в `D:`.
- Файл, который не запустится вовсе, в библиотеку не попадает. На него показывается честное сообщение
  (Problems.dc.html): 16-битная программа для Windows 3.x (формат NE), программа для DOS (нужен DOSBox) или файл без
  заголовка PE.

## Магазины

Магазины необязательны (Stores.dc.html): Steam, Epic Games Store, GOG Galaxy, EA app, Ubisoft Connect.

- **Своя бутылка у каждого магазина.** Это обычная бутылка игры с постоянным id (`Store.bottleID`). Поэтому
  создание, перенос на новый рантайм и сброс работают как у игр, а клиент и его обновления не трогают другие игры.
- **Установка** (`StoreClient.install`):
  - установщик скачивается с сайта издателя по HTTPS. Закрепить его по SHA-256 нельзя, издатели меняют файл с
    каждым выпуском. Поэтому перед запуском проверяется, что это программа Windows (PE) или пакет MSI;
  - установщик кладётся в `C:\windows\temp` бутылки под коротким именем. Пакет Epic с длинным путём
    (`Z:\Users\…\EpicGamesLauncherInstaller.msi`) падает: действие установщика переполняет буфер этим путём;
  - Steam и Ubisoft ставятся молча (`/S`), Epic — `msiexec /qn`, у GOG и EA игрок проходит их собственное окно.
- **Первое обновление Steam.** Установщик Steam кладёт только загрузчик. При первом запуске Steam качается в два
  круга, и каждый заканчивается его перезапуском: сначала старый 32-битный клиент (`cef.win7x64`), затем текущий
  64-битный (`cef.win64`). EscApp следит за `logs/bootstrap_log.txt` и показывает прогресс по строкам
  «(13,352 из 239,614 КБ)». Steam останавливается, когда в логе после `Downloaded new manifest:
  /steam_client_win64` появляется `Shutdown`. Строки `Download skipped` при следующих запусках круг не начинают.
- **Окна на Chromium.** Steam рисует окна через Chromium. Его GPU-процесс рисует в окно чужого процесса, и драйвер
  Wine для Mac показывает там чёрный прямоугольник. `ChromiumHelper` ставит вместо `steamwebhelper.exe`
  обёртку (`tools/chromium-helper/helper.c`, собрана в ресурсы EscAppKit). Обёртка запускает настоящий помощник,
  переименованный в `_real.exe`, с `--in-process-gpu` и программной отрисовкой. Обёртка узнаётся по метке
  `escapp-chromium-helper/1`. Помощник, который вернуло обновление Steam, оборачивается заново при следующем
  запуске. Steam запускается с `-noverifyfiles`: проверка файлов сама вернула бы помощник на место.
- **Игры магазина** (`StoreLibrary`) EscApp читает из записей самого магазина, раз в 15 секунд и при открытии
  экрана:
  - Steam — `appmanifest_*.acf` во всех папках библиотеки, установленной считается игра с битом 4 в `StateFlags`;
  - Epic — `.item` в `ProgramData\Epic\EpicGamesLauncher\Data\Manifests`;
  - GOG Galaxy и Ubisoft Connect — разделы реестра;
  - EA app — `__Installer\installerdata.xml` в папке игры.

  Игра попадает в `Games.json` с `store` и `storeID` и сохраняет свой id, время игры и настройки. Удалённая в
  магазине игра уходит из EscApp. Программа игры нужна для значка и выбора DirectX: её называет магазин (Epic, GOG)
  или EscApp выбирает так же, как после установки.
- **Запуск игры магазина** идёт через клиент: Steam — `-applaunch <id>`, Epic, EA и Ubisoft — свои ссылки. GOG
  без DRM запускается напрямую.
  - Всё в бутылке работает в одном дереве Wine. Если клиент запущен с другим бэкендом, он закрывается: Steam через
    `-shutdown`, через 20 с — `wineserver -k`.
  - Реестр игры пишется, только пока бутылка магазина стоит.
  - Бутылка магазина не затихает, пока работает клиент. Поэтому конец игры — это момент, когда исчезли процессы,
    запущенные из её папки (`StoreGameWatch`, `WineProcesses`). Wine кладёт Windows-путь программы в первый
    аргумент процесса. Окна игры ищутся тоже только среди этих процессов, а «Стоп» завершает только их.
  - У игры магазина одна попытка без тайм-аута на окно: другой бэкенд означает перезапуск клиента, а первый запуск
    может ждать входа в аккаунт или обновления.
- **Игре нужен Steam.** Игра, которая без Steam закрывается, пишет в лог `[S_API FAIL] SteamAPI_Init() failed`.
  `LogDiagnosis` распознаёт эту строку (`needsSteam`), и для игры не из Steam показывается сообщение со ссылкой на
  экран магазинов.
- **Удаление.** Игру из Steam или Epic «Удалить…» (на странице игры и в контекстном меню карточки) после одного
  подтверждения отправляет в Корзину вместе с записью магазина о ней (`appmanifest_<id>.acf`, `.item` и строка в
  `LauncherInstalled.dat`), и магазин видит игру неустановленной (`StoreUninstall`). Открытый клиент сначала
  закрывается и после удаления открывается снова: работающий Steam держит игры в памяти и при выходе записывает их
  обратно. Игру GOG Galaxy, EA app и
  Ubisoft Connect удаляет сам клиент: они хранят свои игры в реестре. «Удалить…» у
  магазина закрывает клиент и удаляет его бутылку вместе с играми. Сохранения в общем профиле остаются.
- **Закрытие клиента.** Крестик в окне Steam (и других клиентов) только прячет окно, а сам клиент работает
  дальше: значка в трее на Mac нет, окно чата открывается само, когда приходит сообщение. `StoreKeeper` каждые 3 с
  смотрит на работающие клиенты, и клиент, у которого не осталось показанных окон, закрывается (`StoreQuit`):
  через 8 с после последнего окна или через 60 с после конца игры (Banished перезапускает себя через Steam за
  27 с). Свёрнутое окно с Mac не отличить от спрятанного, поэтому, когда на экране ничего нет, EscApp спрашивает
  Wine программой `store-windows.exe` (`tools/store-windows`). Клиент, который ещё ни разу не показал окно и не
  запускал игру (тихий запуск ради игры, обновление, вход), не трогается. Пока Steam готовит запуск игры
  (облако, скрипты установки; строки `GameAction … LaunchApp` в `logs/console_log.txt` без `Completed` или
  `Failed`, не старше 5 минут), он тоже считается занятым игрой (`SteamLaunches`).
  Так же и пока Steam качает или обновляет игру: в Windows закачка идёт и с закрытым окном. Последнее состояние
  игры в `logs/content_log.txt` после последнего запуска Steam содержит `Update Running` (`SteamDownloads`). Карточка магазина и экран магазинов
  предлагают «Выйти из Steam» вручную.
- **Зависшие процессы страниц.** Steam перезапускает свой `steamwebhelper`, а в Wine процессы страниц старого
  браузера не завершаются вместе с ним: за 48 минут их осталось 15, каждый ел пятую часть ядра. `SteamHelperSweep`
  завершает процессы помощника, запущенные раньше самого нового браузерного процесса.
- **Снимки экрана игры из Steam.** Раздел «Снимки экрана» на странице игры (Game.dc.html) для игры из Steam
  заполняется снимками с её страницы в магазине: публичный запрос `store.steampowered.com/api/appdetails` называет
  только номер игры (`SteamScreenshots`). Список и маленькие картинки лежат в `Artwork/steam-<номер>`, список
  обновляется раз в неделю, полный снимок качается при первом открытии. Каждая сверка магазинов удаляет папки
  `Artwork/steam-<номер>` игр, которых больше нет в списке (удалены в EscApp или в Steam, удалён сам Steam). Картинки берутся только с серверов Steam
  по https. Просмотр закрывает всё окно, стрелки листают, кнопка «Во весь экран» (или F) разворачивает окно,
  Esc закрывает и возвращает окну прежний размер.
- **CLI:** `escapp store list | install | open | close | remove <магазин> | sync`.
- **Проверено на Wine 11.20:**
  - Steam ставится одной командой примерно за 50 с, вход в окно рисуется;
  - запуск игры магазина проверен тестом `StoreProbeTests` (проба в бутылке GOG рядом с работающим «клиентом»);
  - Epic ставится одной командой примерно за 4,5 минуты, вместе с первым обновлением лаунчера, и открывается на
    странице входа (Wine 11.20 сборка 2). Чтобы так было, понадобились три вещи (`StoreClient+Epic.swift`):
    - **Самообновление.** Лаунчер скачивает новую версию в `ProgramData\Epic\EpicGamesLauncher\Data\Update\Install`,
      закрывается и оставляет окно «Установка обновлений» (`EpicGamesUpdater.exe start`). Установку должна сделать
      его служба, но в Wine её шаг `-Commandlet=selfupdateinstall` сразу завершается с кодом 777006, и окно ждёт
      вечно. Тот же шаг, запущенный от имени игрока, проходит. Поэтому EscApp запускает его сам: при установке,
      перед любым запуском, если в папке обновления остались файлы, и пока лаунчер работает после «Открыть».
    - **`-opengl`.** С Direct3D-отрисовкой Unreal страницы магазина не появляются поверх логотипа: GPU-процесс
      Chromium не стартует («Failed to launch GPU process» в `cef3.log`). Обёртка `ChromiumHelper` здесь не годится:
      у Epic браузерный процесс — сам лаунчер, и с обёрткой падает сетевая служба Chromium.
    - **Сторож.** Примерно один запуск из трёх так и остаётся на логотипе: в его логе нет ни одной строки
      `LogWebView`. Если за 75 с страницы не появились, лаунчер перезапускается, до двух раз. Быстрая синхронизация на это не
      влияла: с ней и без неё доля была одинаковая;
  - GOG Galaxy, EA app и Ubisoft Connect на Wine ещё не проверены.

## Интерфейс

- **Главное окно:** широкие карточки игр в две колонки: иконка из exe (она есть у каждой игры) на квадрате светлого
  оттенка её основного цвета, название, когда и сколько играли, откуда игра (метка магазина или «с диска»). Справа
  всегда видны «Об игре» (страница игры) и «Играть». Щелчок по названию тоже открывает страницу игры. Сверху
  фильтры по источнику и порядок. Установщиков в списке нет никогда: открытый установщик сразу ведёт на экран
  установки, а в список попадает уже установленная игра. Отдельной зоны для перетаскивания нет: внизу одна строка-подсказка, что
  игру добавляет двойной щелчок по .exe/.msi или перетаскивание файла на значок EscApp в Dock (на окно тоже можно).
  Сверху статус компонентов, только если что-то не так.
- **Страница игры:** «Играть», «Открыть папку игры», ярлык в Launchpad, «Удалить…». Сведения: папка, какой exe
  запускается (можно сменить), размер игры, реальный размер среды Windows, сохранения (размер, «Показать»), версия
  Windows, графика, сколько сыграно, когда добавлена. Снимки экрана и последние запуски с результатом и логом.
  Раздел «Дополнительно» (отдельный экран): бэкенд, Retina и масштабирование (Авто/Вкл/Выкл), переменные окружения,
  параметры запуска, Cmd как Ctrl, лог, сброс среды.
- **Откуда игра** видно везде: на плитке в главном окне (метка магазина: Steam, Epic, GOG Galaxy, EA app, Ubisoft
  Connect; у игр с диска метки нет) и в сведениях на странице игры («Откуда»: магазин, образ диска, папка). Игры
  магазина EscApp находит в его среде сам (манифесты Steam, Epic, GOG Galaxy) и запускает через клиент магазина.
  Удаляются такие игры как описано в «Удаление» выше.
- **Удаление игры** (с диска, не из магазина) — два варианта:
  - *Только из EscApp* (по умолчанию): удаляются запись в `Games.json`, бутылка и файл `.escapp`. Папка игры и сохранения
    остаются. Двойной щелчок по exe добавит игру заново.
  - *С диска*: папка игры уходит в Корзину (не стирается насовсем). Сохранения по умолчанию остаются; удалить их тоже —
    отдельная галочка.

Откуда берутся данные для страницы игры:
- **Сохранения игры.** Профиль общий, поэтому EscApp во время каждого запуска запоминает, какие файлы игра создала или
  изменила в профиле и в своей папке. Так он знает размер сохранений конкретной игры, может их показать и удалить.
- **Снимки экрана:** файлы картинок, которые игра пишет в свою папку или в профиль (их находит тот же учёт файлов),
  и снимки, сделанные во время игры через EscApp. Хранятся в `EscApp/Screenshots/<game-id>/`.
- **История запусков:** из логов (`Logs/<game-id>/`): дата, длительность, бэкенд, итог.
- **Первый запуск:** проверка и установка компонентов одним экраном.
- EscApp регистрируется как программа для `.exe`, `.msi`, `.iso`.
